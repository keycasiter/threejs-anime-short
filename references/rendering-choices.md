# 渲染、材质与成品表达的技术选择

用于灯光/材质升级、渲染器迁移、产品镜头或参考demo拆解。选择以目标项目锁文件、实际安装包、官方文档和必要能力验证为准，不把历史demo的版本当成当前兼容性保证。

完整制作的材料目标、受控对照、截图配对及放行方法见[材质与灯光校准SOP](lookdev-calibration.md)；本页用于按目标需求选择渲染路线并核对实际消费者。

## 先确定画面依赖什么，再选引擎能力

| 路线 | 成品表达依靠什么 | 适用条件与代价 |
|---|---|---|
| 烘焙场景 + unlit | 外部建模、UV、离线照明已写入颜色贴图；运行时只负责展示与局部动画 | 静态布景运行成本低；移动物体的动态投影、反射和受光必须另做 |
| MatCap/风格材质 | 受控法线、材质族、定制明暗和专门阴影 | 相机空间MatCap不会自然响应真实世界光位，动态投影需单独组织 |
| PBR + IBL | 资产比例与边缘、合理roughness/metalness、环境反射带、接触阴影 | 适合多视角和真实材质；环境贴图不会修复缺少倒角、厚度或错误法线的模型 |
| 自定义节点/绘画管线 | 把主明暗、环境反弹色、雾、水线、描绘规则组织为统一材质/缓冲契约 | 反弹色、材质阴影与投射阴影需整体接通；单个shader不代表整套画风成立 |
| 路径追踪 | 多次反射、折射、间接光及累积采样 | 可用于慢速离线关键镜头；耗时、噪声、动态场景更新、收敛和导出协议均不同于实时光栅 |

路线可以混合，但需明确每层贡献。研究阶段从已有证据解释贡献；实施诊断时根据症状选择灰模、固定材质转灯或固定灯光换材质中能回答当前问题的最少干预，不固定执行整套实验。成品的主体层级、留白、反射带和细节尺度需有设计；添加更多库不会自动改善它们。

## 后端与版本是接入约束

迁移前记录：Three精确版本/单一模块实例、renderer类、实际backend、材质类型、自定义GLSL、MRT布局、后期栈、深度/透明约定、目标设备及输出格式。addons、类型包、R3F/drei、postprocessing和BVH的peer范围要逐项核对，不能把`@types/three`或devDependencies当运行版本。

| 环境 | 已确认的边界 | 实施方式 |
|---|---|---|
| 传统WebGLRenderer + GLSL | 保留已有ShaderMaterial、RawShaderMaterial、onBeforeCompile与自定义MRT契约 | 新效果先在原栈做小探针；不能把TSL compute直接放进旧GLSL链 |
| WebGPURenderer | 由`three/webgpu`导入，异步初始化；可用WebGPU或WebGL2后端 | `await renderer.init()`后检查实际backend；WebGL2回退不等于旧WebGLRenderer，也不保证任意计算节点可用 |
| 节点/TSL桥接 | 桥接接口和能力随版本变化，按实际安装包/示例核对 | 不推断旧GLSL/MRT/全部TSL功能可无缝混合 |
| WebGPU后期 | 类名、节点输出和初始化接口随版本变化，不能混用不同代教程 | 跟随对应版本迁移指南，不能拼接不同代API；TSL旧`tslFn/timerGlobal`示例应迁移为安装版接口 |

已有成片升级时，先保留可运行基线。为新后端建立独立入口，验证初始化、一个真实材质、一个MRT消费者、一个目标效果和导出。比较输出及成本后再迁移主项目；仅初始化成功不能证明整条管线兼容。

### 教程迁移时核对实际消费者

| 教程写法/假设 | 当前实现选择 |
|---|---|
| 依赖PBR默认值 | 显式写设计值，并查看实际安装版；r180的MeshStandardMaterial默认metalness=0、roughness=1，不照抄教程中的默认0.5 |
| `texture.encoding`、`renderer.outputEncoding` | 现代版本按`texture.colorSpace`、`renderer.outputColorSpace`及实际末端pass接入；JS对象能添加旧属性不证明renderer读取了它 |
| EffectComposer末端再加旧GammaCorrectionShader | 先确认当前线性/HDR/tone mapping/输出链；Three原生现代Composer通常用OutputPass，不能与旧校正机械叠加 |
| 调`shadow.radius`就会变柔 | 按灯型与shadowMap.type确认；r180方向光PCFSoft路径不使用此radius，PCF使用。点光路径不同，不能推广到所有灯 |

用小型真实像素探针核对字段/通道：编码、粗糙度G、法线方向和阴影参数都应追到消费者；再在目标场景里评效果。

## 色彩、曝光与后期：记录数值所处空间

常规PBR链：颜色输入解码 → Linear-sRGB工作空间 → HDR光照/合成 → 需要的tone mapping → 输出颜色空间。baseColor/emissive颜色贴图通常标sRGB；normal、roughness、metalness、AO、mask等数据贴图不做颜色解码。HDR与渲染目标按真实编码处理，不给所有texture统一设置sRGB。glTFLoader已处理多项语义，勿再覆盖。

Three原生EffectComposer中，线性中间结果通常由末端OutputPass完成tone mapping和输出转换。pmndrs/postprocessing是另一套契约：按其版本配置renderer输出、HDR buffer和ToneMappingEffect；不能机械地再塞Three的OutputPass。自定义绘画管线若有自己的曝光/输出编码，先读已有契约。

区分scene-linear效果和display-space效果：HDR阈值bloom通常需要映射前亮度，文字/颗粒可能需要显示空间；明确每个pass的输入输出。不要因某参考写了`renderOutput`就再统一追加转换。透明离屏捕获也要防止先tone map再主合成而重复映射。

最小探针：无光照纯灰色、固定曝光与分辨率，比较直出与完整后期，分别移除/重复末端转换作负对照。数值应与目标颜色契约相符；不把某管线结果变成所有管线添加输出转换的规则。

## PBR/环境表达与资产准备

优先把可见质量落实在资产：有读得出的轮廓、边缘厚度与法线；UV/切线正确；同一材质族的粗糙度、细节尺度、纹理密度一致。近景检查掠射反射，远景检查主次；用高roughness、单色环境和无后期版本定位问题。

`scene.background`决定看见的背景，`scene.environment`影响环境照明/反射，两者不能互相替代。光栅PBR的环境需正确预过滤（如PMREM；也可能由renderer自动处理，按版本确认），否则粗糙表面反射不成立。设计大面积亮暗反射带和主辅光关系，再调曝光；清漆、各向异性、transmission分别有额外计算与资产要求，按镜头需要启用。

选择PBR贴图时先查看实际图像与通道语义，确认它描述的是材料本身还是已经包含整段装配。照片中的砖缝、板缝等宏观结构若又铺到逐块建模表面，会形成重复构造；改选适合的材料扫描、分区取样或程序场。把一个tile对应的实际尺寸写入UV/采样变换，按上节色彩语义接通通道，再在最终景别查看比例和重复。

场景中的可见主光、投影主灯、IBL及水/雾等方向性响应由同一个环境意图派生；区分世界方向向量与灯的位置/target，附加补光明确其用途。局部捕获的far与图层需覆盖预期环境，捕获内容按下表记录。用真实曲面看宽窄反射带与接触暗部，再决定粗糙度和曝光，不能用总亮度替代体积塑造。

读取glTF、解码器、压缩纹理、动画及资源生命周期的完整流程见 [motion-and-scale.md](motion-and-scale.md)。代码许可和HDRI/模型/纹理许可分别核对；开源展示不自动授予所有资产复用权。

### 从画面任务分配灯光角色

先指出需要读出的曲率、接触、负形和前后层，再安排发光方向、受光范围与反差。角色是画面用途，点光/聚光/方向光/面积灯是实现能力；同一用途可选不同表示，不要求每场凑齐固定灯数。

| 画面任务 | 实现选择与设计输入 | 在实际曲面看什么 |
|---|---|---|
| 主要塑形与接触 | 有方向的主光、目标区域与支持的投影；按所选管线设计柔和度 | 转折两侧、承接与接触暗部可读，亮面不吞掉结构 |
| 暗部信息与整体受光 | 环境、半球或受控局部补光；强度和覆盖配合主光 | 暗部保留所需信息，同时保住形体反差 |
| 材料反射带 | HDRI/PMREM、面积光或真实局部捕获；安排亮暗区域的方向与宽窄 | 金属曲率和粗糙区被揭示，不只增加白色高光 |
| 主体与空间分层 | 有意的轮廓/背景受光及可信来源，连同相邻背景一起安排 | 焦点与背景分开，换侧背视角仍有有用内容 |

核对当前后端能力再移植DCC布光：本页核对的r180 WebGLRenderer中，`RectAreaLight`需初始化LTC并作用于PBR，具有面积光受光响应而没有投影阴影；反光板间接反弹或独立光线可见性也需相应渲染表示。柔和投影、间接光与宽反射分别选支持它们的方法，不能互相冒充。

校准时固定几何、表面材料、相机、曝光和输出，比较少量有明确意图的照明方案；局部变清楚与整幅更接近目标分别判断。记录局部环境捕获是否随新布光刷新。r180 `WebGLRenderer`的内建Standard/Physical材质中，非空`material.envMap`优先于场景环境，使用`material.envMapIntensity`；回退到`scene.environment`时使用`scene.environmentIntensity`。按实际绑定追查，避免无效调参。选定后重看相邻时刻与观看包络，已有相同证据可继承。

## 从目标响应接到实际消费者

对当前决定品质的材料/自然效果，先选出要表达的响应，再接通它的数据链：**形成原因与区域/方向/尺度 → 几何或场 → 材质通道/渲染状态 → 光照或捕获来源 → 最终像素**。将这条链写进现有特征映射，按瓶颈选择条目，不给所有材料机械增加同一套贴图。

| 目标响应 | 生成与接入方法 | 有区分力的局部检查 |
|---|---|---|
| 凹凸、颗粒与折转受光 | 轮廓/厚度/大褶皱进几何；微高度求normal/bump，粗糙区进roughness；颜色独立。字段烘焙见[表面方法](surface-detail.md) | 固定几何、机位与光，按问题关闭一种通道；颜色有斑而受光不变时先查消费者/方向/尺度，不先加噪声 |
| 薄层透见、遮罩和体积透射 | 按目标选alpha混合、裁切/抖动覆盖或transmission；明确深度写入、排序和需要的捕获/厚度。alpha进入混合需对应透明路径，shader输出alpha本身不充分 | 在带前后遮挡物的实际样件看前/后和掠视，核对本项目版本的[Material状态](https://threejs.org/docs/pages/Material.html)；不能一律关闭depthWrite或把所有玻璃改transmission |
| 金属/涂层/湿面的反射内容 | 主辅光与环境亮暗带共同设计；列清IBL/局部捕获实际包含什么，按需要选择天空、布光环境或场景捕获 | 实际曲面与最终环境中看反射带是否揭示中层；PMREM对传入环境预过滤，不会自动把未捕获的场景加入反射 |
| 连续介质及触发反馈 | 来源、沿程包络/截面、局部破裂/覆盖、接触足迹和强度从共享场/锚点派生；实体/薄层/碎屑/雾各用合适表示 | 静帧看外形与厚度，连续片段看来源到接触反馈；颜色滚动、独立圆环或粒子数量不能证明流动形态和反馈关系成立 |

链路尚不确定时，在同构建副本只切换相关状态/通道，固定几何、种子、机位与时刻，确认预期区域确实变化；保留原状态。单变量诊断证明的是参数作用范围，最终是否更好仍回目标图与整镜判断。新反射场与新表面场分别验证，避免联动替换后无法定位。已确定且无相关缺口的通道无需重复探针。

### 薄层与透射先选一种表示

先依据目标选择：alpha混合适合受控薄层叠加；需要透射及保留反射响应时使用支持该路径的Physical材质。以本页核对的r180为例，`MeshPhysicalMaterial`启用非零`transmission`时保持`opacity: 1`，不要把它同时当作另一个透射强度旋钮；当前[官方材质说明](https://threejs.org/docs/pages/MeshPhysicalMaterial.html#transmission)亦有该约定。

```js
// 薄玻璃的起点，非通用成品参数；由实际厚度、反射和遮挡继续校准。
const glass = new THREE.MeshPhysicalMaterial({
  transmission: 1, opacity: 1, transparent: false,
  roughness: .08, metalness: 0, thickness: 0, ior: 1.5
});
```

仅为alpha覆盖混合时再开启相应透明路径，明确排序与depthWrite；不能把所有玻璃统一关闭深度写入。以玻璃后的实际物体作代表样件，先固定灯光切换玻璃状态，再固定玻璃比较局部受光；不要同时调整灯强、颜色、透明度和曝光后归因。接收面本身不亮、透视层压平颜色、环境/曝光压平反差是不同问题。多层玻璃和屏幕外信息仍受下表的捕获限制；该配置不保证完整物理透射或最终品质。

## 软阴影、玻璃与反射的成本不是一个参数

| 机制 | 数据链与可迁移用途 | 失败条件及验收 |
|---|---|---|
| ContactShadows | 俯视深度捕获 → 模糊 → 地面叠加；便于建立贴地关系 | 捕获near/far、范围、分辨率影响形态；有限frames会冻结。检查移动后位置、物体离地高度和帧跳转；不替代任意场景的物理软阴影 |
| AccumulativeShadows | 多个扰动光位反复更新lightmap，形成柔和阴影 | 有历史状态；seek/换姿势后clear/reset并按固定种子重采样。temporal渐进不能直接取第一帧；动态阴影不能沿用旧姿势的累积 |
| 动态Environment | CubeCamera捕获虚拟场景供反射/照明 | drei默认frames=1可冻结；移动内容需更新策略。六向捕获有成本，避免自身反馈和错误层；离线按镜头确定更新时机 |
| 屏幕/缓冲透射 | scene捕获 → 折射投影采样；drei材料可另做背面和主buffer | 多个额外scene render；屏幕外、遮挡与多层玻璃存在信息缺口。检查厚度/IOR/法线、前后排序、重叠玻璃、相机切换和HDR；质量差时先区分几何与屏幕信息限制 |
| 平面反射 | 镜像虚拟相机 + 裁剪面 → texture投影/模糊/深度混合 | 适合近似平面，不等于任意曲面真实反射；材质类本身不自动完成相机与捕获更新。计算额外相机的draw calls，切镜后刷新 |

drei是R3F组件，`@pmndrs/vanilla`提供部分非React实现；移植时要同时适配生命周期、scene捕获和资源释放，不能只复制材质定义。多遍渲染必须保存并恢复render target、visibility、background、tone mapping等状态，失败或早退也要恢复。

## 可调用的离线柔和主光

当目标需要柔和投影而实时PCF仍太硬，可选用[直接光采样模块](../assets/rendering/soft-directional.mjs)。这是独立实现的有限采样光栅工具：固定场景/相机/姿势，围绕同一方向光做等面积盘采样，每次重绘阴影和场景，在线平均线性Float32 HDR，末端只做一次tone mapping及输出转换。它改变直接光与投影，不增加间接反弹；设计、材质或结构缺失仍需在各自层修复。

```js
import * as THREE from 'three';
import { renderSoftDirectional } from './soft-directional.mjs';

window.__FILM = {
  duration: 6, fps: 24, audio: 'none',
  capture: { mode: 'awaited', timeoutMs: 120000 }
};
window.renderAt = async t => {
  evaluateSceneAt(t); // 完整求值姿势、相机、FX和DOM，暂停独立RAF
  scene.updateMatrixWorld(true);
  const done = await renderSoftDirectional({
    THREE, renderer, scene, camera, light: key,
    samples: 64, angularRadius: 0.10, seed: 123
  });
  return {
    complete: true, time: t,
    completedSamples: done.completedSamples,
    requiredSamples: done.requestedSamples
  };
};
// 必需资产/字体准备好后，再置 window.__ready=true。
```

将模块复制到作品源码并调整相对导入；`THREE`由调用者注入，不自带第二份引擎。已验证路径限定为Three 0.180.0的`WebGLRenderer`、默认canvas target、XR关闭、支持float color attachment、单个可见投影灯的内建颜色链；入口拒绝版本/target/其他投影灯不符。它是可选实现，不能为了使用它强制迁移既有项目。Composer、自定义GLSL、WebGPU、透明canvas及复杂多层透射需另适配。末端统一转换可能改变背景或`toneMapped=false`材质的直出语义，不能预设全场景像素等价；必要时保留独立显示空间合成。

`samples`整数1–256，`angularRadius`弧度0–0.25；N=1取原灯方向，零半径多样本用于管线等价检查。先比原直出与新管线N=1，再比较同一管线N=1与多样本，避免将MSAA/输出差异误记为采样收益。检查投影接触是否保留、半影是否有分层/闪烁、原阴影相机是否仍覆盖扰动方向；不要把64样本或某个角度定为全项目最低品质。

调用期间冻结全部可见状态并串行渲染。模块用WebGL2 fence等待每样本及末端输出，成功或失败均恢复约定的renderer/主灯状态并释放临时资源；`onSample`供进度观察，不得改变场景。它每次分配临时target，适合已测成本的离线帧；先测代表镜头和相邻帧，再估全片耗时。原尺寸审图仍决定是否采用，采样完成本身不证明整场跨品质档。

## 路径追踪与异步导出

路径追踪器的不同后端可能有不同入口、材质支持和更新API。先核对当前版本的支持列表、场景快照/更新、完成状态和降噪协议；下面列出必须处理的职责，不将特定库版本的命名作为通用契约。

区分初始场景捕获、相机更新、矩阵更新、材质/灯光/环境更新和累积重置，分别映射到所选库实际支持的接口。蒙皮、morph等实际顶点变化需按该版本更新几何快照或重建场景，不能当作矩阵变化；清空累积不等于同步几何。大场景可采用库支持的worker BVH构建；给同步调用包一层Promise不会把计算移出主线程。

每个输出帧的契约：

```text
absoluteTime → 完整求值姿势/矩阵 → 同步对应场景数据并使累积失效
→ 固定种子/采样预算 → 持续渲染至全部像素达标
→ 等待附加denoiser完成 → 捕获 → 才允许前进到下一帧
```

设置有限采样预算；完成信号必须覆盖目标像素的采样预算和附加降噪结束，平均sample数或某次draw完成不足以证明收敛完成。无限渐进模式需显式停止条件。等待需有超时、取消、GPU错误与失败重试边界；稳定噪声也不保证跨设备位级一致。比较几帧的单帧耗时、闪烁、折射细节、降噪残影和可接受噪声后再估全片成本。

`scripts/render_film.mjs`默认使用同步`renderAt(t)`；显式声明`__FILM.capture.mode="awaited"`时才等待逐帧完成报告与固定预算，再截图，接口见[离线导出](validation.md#可执行离线影片导出)。导出器不替具体库实现场景同步、累积重置、GPU等待或降噪；这些职责由适配器完成。线性录制中的`mixer.update(dt)`还需适配为可随机取帧的姿势求值。
