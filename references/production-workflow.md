# 从需求到最终作品的生产流程

本页是主链路的详细执行说明。技术做法进入各自参考，放行标准统一由[验收](validation.md)定义；项目只保留一份制作规格和一条主时间线。

## 制作记录与依赖

在项目现有目录保存一份可更新的制作规格。篇幅随作品规模缩放，至少覆盖：

| 区块 | 内容 |
|---|---|
| 目标与依据 | 观众、用途、情绪/信息、事实与风格参考、未知项、来源/许可 |
| 画面与资产 | 视觉目标板、画幅/景别、焦点、形体/材料/空间关系、设计取舍、资产路线与像素细节 |
| 空间与时间 | 单位/轴向/原点、相机模式及包络、镜头/cue、主体/接触锚点、字幕安全区 |
| 运行与交付 | Three.js与依赖版本、渲染入口、时钟、声音状态、HTML/源码/视频、目标设备与预算 |
| 完成依据 | 质量卡对应的当前构建画面、连续动作、相机操作、资源/媒体检查与未覆盖状态 |

同时按用户请求范围初始化 `delivery-manifest.json`，阶段ID、输入输出哈希和运行/审阅字段见[阶段交付契约](delivery-contract.md)。更新manifest时只记录真实完成的阶段状态；完整制作需从Skill安装目录调用`<skill-root>/scripts/validate_delivery.py <project-root>/delivery-manifest.json --through spatialProxy`，以本脚本输出作为正式资产开工凭据。

## 生产阶段与放行

### 0. 方向提案

开放式需求先提取已确定项和真正开放的设计变量，提出至少5个有实质差异的方向。用生成图做清楚分格的方向板，每项配画面描述、推荐理由、Three.js实现抓手、事实/风格依据和取舍；工具不可用时说明形式限制，给可比较的文字/构图板。请用户选择或混合方向。用户已明确方向或要求直接执行时，记录选定项或合理假设后推进。

方向图只用于比较设计，不证明真实结构与尺寸。选定后才进入详细资产设计；不要把多个候选全部制作成场景。

### 1. 制作规格与视觉基准

先写观众将看到什么、看清什么、发生什么变化，再定时长、画幅、输出与相机模式。短单镜可默认约5–8秒、16:9、24fps、自包含HTML；教学/叙事按事件需要定长。

把质量目标落实到实际视觉目标板：用户选定图、可靠对象/成片图、设计生图或有表达力的结构/色彩稿。全貌规定构图、体积、空间层次和光区；局部规定决定品质的结构、边界、材料响应。没有用户参考时自行建立并选择，不重复索取已确定方向。生成图是设计提案，真实尺寸/连接/物种等事实另行核对。图像索引只证明参考文件存在；还必须建立`visual-build-map.json`，逐个可渲染对象/路径记录视觉观察、可检查约束、Three.js形体表示和命名组件。Stage 1结构验证要确认每个登记对象/路径都已映射。

在规格里分别写“要保留的视觉关系、允许有意改变的设计、事实未知项”。用局部差异解释精细度：例如连续体积与薄片、真实连接与邻近摆放、层次受光与统一底色、材料反射带与高光白块；不把面数和数量作为品质目标。当前代码第一帧可以用于排错，不能自动成为质量基准。实际使用的全局和局部参考保存在`references/`并登记到`design/visual-reference-index.json`，覆盖方向、各可渲染对象/路径、关键连接和材料问题；`visualAnalysis`阶段同时哈希登记表和图像索引。细节和图像生成方法见[视觉分析SOP](visual-analysis-sop.md#build-the-visual-reference-packet)。

**产物：**制作规格、全貌/关键局部的视觉目标板、来源/设定与取舍、完整`visual-build-map.json`。缺少视觉依据时标记“视觉基准待校准”，技术探索可继续，但不宣布参考级或高品质已验证。

### 1A. 视觉分析交接后的运行预检

在制作对象专属Three.js几何前，先运行最小场景预检：加载计划使用的Three.js核心和同版本addon，创建renderer、放置一个简单标准几何与光，运行目标浏览器并实际捕获canvas。确认WebGL/WebGPU初始化、依赖可达性、本地服务和目标输出方式。根据最终交付是否需要离线，选择本地bundle/随附文件或明确依赖网络的固定CDN版本；把它记录进runtime preflight报告。离线ESM必须复制完整传递导入依赖或先bundle，不能假定单个入口模块独立；保留许可证。预检报告要基于真实运行的错误/失败请求和canvas，模块文件存在或静态图检查都不能代替浏览器初始化。不要把依赖解析和浏览器启动留到正式资产完成后才发现。

预检记录浏览器和Three.js版本、renderer backend、依赖策略、console错误、失败请求与canvas截图。若失败，先排除兼容/服务/依赖路径问题；不能恢复时停在预检，不进入场景专属正式资产。完整报告字段与阻断行为见[阶段交付契约](delivery-contract.md)。

**按固定顺序诊断预检阻断，避免把网络故障直接当成依赖不存在：**

1. 读取项目锁文件，确认目标Three.js、addon、构建器和浏览器自动化版本；优先复用项目内已锁定且兼容的依赖，不升级到浮动版本。
2. 检查依赖是否已安装，再检查当前包管理器的本地离线缓存/存储。使用与项目匹配的包管理器离线查询；npm项目可先运行`npm cache ls three`。只有缓存中确有锁文件指定版本且完整性可核对时，才尝试离线安装。缓存索引命中、其他版本存在或npm报错都不能单独视为依赖已恢复。
3. 检查允许使用的浏览器与自动化运行时是否已安装，并记录实际可执行文件和版本；浏览器存在仍需启动目标页并验证WebGL/WebGPU、请求与canvas。若headless Chromium能启动但没有创建WebGL上下文，可在可信的本地QA页面上尝试显式软件渲染：`--enable-webgl --ignore-gpu-blocklist --use-gl=angle --use-angle=swiftshader`。读取实际renderer/backend并确认canvas确有像素；SwiftShader通过只证明软件路径可绘制，不证明目标硬件性能。Chrome/Chromium版本变化时按[Chromium SwiftShader说明](https://chromium.googlesource.com/chromium/src/+/main/docs/gpu/swiftshader.md)核对当前参数；不要为了绕过浏览器策略而在不可信页面上启用unsafe fallback。
4. 对registry/CDN失败只做一次有针对性的本地恢复检查，不循环重试同一不可达地址。共享缓存权限异常时，不用`sudo chown`或修改全局缓存所有权；仅在可验证锁文件完整性时使用项目隔离的本地包，否则保留阻断。

Playwright管理的Chromium若因操作系统权限/沙箱错误不能启动，或只能启动却无法连接调试端口，应归类为`browser startup`故障，不是WebGL renderer失败；不要继续更换SwiftShader参数碰运气。检查当前环境是否允许用已安装的Chrome/Chromium二进制以headless方式启动，并通过Chrome DevTools Protocol或已提供且适用的浏览器MCP/CUA驱动同一个可信本地预检页。使用独立临时profile，记录实际浏览器版本、目标页URL、renderer、canvas尺寸/像素、脚本错误和失败请求；如果通过`file:`加载本地ESM，优先改用本地HTTP服务，否则仅对可信本地页启用文件访问。切换执行器后仍须从目标页面实际读回canvas，不能把浏览器进程启动或页面返回HTTP 200当作预检通过。没有其他允许的执行器或所有执行器均失败时，按实际失败阶段记为BLOCK并停止。

报告应区分`缺包`、`缓存不可用`、`无浏览器`、`浏览器启动失败`、`renderer初始化失败`和`本地服务/路径失败`，并指出下一步最小恢复动作。缓存检查不能替代真实运行门槛；找不到可用浏览器或canvas时，`runtimePreflight`仍为BLOCK，完整制作仍停在该阶段。

### 2. 场景、资产设计与方案选择

先从用途与目标板建立全场空间计划，再选实现。按[资产设计](asset-craft.md)及[构图/空间/中层方法](composition-and-form.md)确定分区/路径/边界、前中远组、主体尺度与光区。真实场地用可靠平面/尺寸约束位置；虚构场景先设计平面与侧向层次。叙事只在需要时转成空间段落，不强加故事或CAD。

把开工输入分成三个相连的数据层，放在现有规格/代码中：

| 数据层 | 先做出的设计 | 实际消费者 |
|---|---|---|
| 空间计划 | 场地边界、通行/使用区、承载面、组中心/范围/形态族、主次光区 | 地形/路径网格、资产落点/朝向与相机；背景和主体同时进入代理 |
| 资产结构 | 主轮廓与关键截面、交界/开口、连续/分件方式、接触锚点 | 顶点/拓扑/模型、局部框架、变形和反馈；每个重要差异能独立改变 |
| 材料区域 | 构造/生长/加工或使用形成的区域、方向和尺度 | 颜色/粗糙度/金属/法线及对应受光；区域与几何/UV保持一致 |

对同一空间规律会影响两个或更多系统的任务，在规格里写清它的数据来源与消费者。连续变化（如坡度同时影响地表断面、岩块落点和植被密度）用同一语义场或可复算函数；离散构图（如池岸、桥、亭、步道的相对位置）用共享布局表、曲线或组件规则。记录坐标空间、单位、seed（如有）、遮罩/权重，以及具体的几何、散布、材质或FX消费者。没有共享驱动时明确采用独立设计输入；不要为了形式创建无用途的场。

进入中层形体时，从场景登记表将每个实际可渲染对象与路径纳入[资产族台账](delivery-contract.md#runtime-and-review-evidence)，按焦点、支撑、环境资产分族，并为每族写具体可见的检查标准。重复实例可共用族，但母版形态和最难审的实例/方位都要有独立证据。最终审图逐族绑定当前运行截图；整体构图通过不能代替对象族的形体、连接、材质与细节验收。使用`assets/templates/asset-ledger.template.json`起步，并把`assetLedgerPath`写入manifest。

代表样件选一段完整关系：既包含决定身份的主体结构，也包含相邻体块、承载及判断所需环境。先核对所选生产工具能实际产生/修整该资产；外部模型路线按[资产准备](ai-asset-pipeline.md#先确认资产生产链能实际完成)准备并在Three.js中看效果，不能停在工具名称。扩展完整资产前，按visual-build-map选出每个不同形态族的代表件，完成形体、过渡、连接、材料区域和必要承托；在目标尺寸下捕获至少两个互补视角的真实PNG，与指定参考图逐特征对照并记录差距。逐特征记录 `viewIds`：剪影/比例/体积必须关联主视角和补充形体视角，连接必须关联接点近景和能说明延伸方向的侧/斜/背/底视角，空间关系必须关联环境视角和侧/斜/背视角。只重复英雄视角不能证明厚度、连接或前后关系。源码、截图路径及哈希进入同一middleForms证据。对焦点资产或独特环境形态未完成此门禁时，不进入规模化细节生成。

对尚未确定且会改变品质上限的选择，做少量有针对性的方案比较，例如整体体量与深度组织、关键资产的构造方式、光区/材料分配或代码/模型路线。用草图、灰盒、多视图或局部样件使差异可见，说明为何所选方案更接近目标；方向已经确定时，这属于内部设计，不重新让用户选题。已被用户或可靠设计锁定的决定直接继承。

建立“目标图可见特征 → 选定设计 → Geometry/Material/Shader/布局或资产 → 对应视角”的映射。多视角图核对比例、数量和连接；视图漂移与未见背面标为假设。代理布局真实取帧后，进入阶段3先按可见资产族建立完成台账（代理、正式制作、场景验证）；每族完成一个包含身份轮廓、中层结构、材料响应和承接关系的正式代表件，并在完整场景校准后才扩展。最终构建必须清零临时代理/灰盒；有意的风格化简化须在质量卡中给出形态规则并经目标视角验证。预算不足时减少次要资产或镜头范围，不用占位资产凑齐场面。

新场景或缺少当前构建布局证据时，第一项实施任务是完整代理场景取帧；已有场景可核对并继承同目标、同构建、同机位/包络的通过证据。相机、布局或主体比例是待优化项时，在该阶段重选对应设计并实际取帧；其他已有证据的场景从阶段3处理尚未验证的质量瓶颈。**进入中层形体前，执行[空间白模执行与放行](spatial-blockout.md)：先按几何类型选表示/工具，再构建白模，并分开记录数据、几何和视觉检查。**自由环绕任务先完成[360°观看环设计](composition-and-form.md#自由环绕先设计完整观看环再建场景)，将相机包络变成空间计划的一部分：

1. 只写最小渲染入口、目标相机、稳定坐标和全场景代理体；从同一空间计划生成主要体积、支撑、前中远景、建筑边界和大明暗块，此时不写正式细节生成器或复杂材质。
2. 实际运行并捕获目标视口；自由环绕需先检查完整相机包络的中性代理图，而非只检查默认机位。冻结源码快照、列全代理组件及资产计数、保存同构建的图像审查，再运行空间门禁；代理门禁通过前不得开始正式资产。修正空间拓扑、相机轨道和各方位内容后，再看最易暴露问题的俯仰/距离边界，调整占幅、遮挡、地平线和安全区。具体字段和命令见[空间白模SOP](spatial-blockout.md#freeze-and-release-the-spatial-proxy-stage-before-formal-assets)。
3. 自由相机同时核对水平/俯仰/距离与合法视锥覆盖，分离影片和自由相机写入权；布局可达范围决定后续几何/环境与光影需要覆盖什么。

**产物：**选定方案、特征/资产台账、实际代理场景渲染与结论（或核对继承的当前构建证据）、空间接口和相机包络。只有文字草图、未运行的代码或后来细化的最终图，不算本阶段已经执行；工具故障保留未完成状态及实际原因。

### 3. 代表画面实现与差异校准

固定视觉目标、机位/景别、种子与分辨率。先选择当前最影响画质、尚未解决的问题，再实现代表样件：

| 动作 | 怎样完成 |
|---|---|
| 选问题 | 对照目标指出具体区域与差距，区分是机位/布局、结构表示、材料/光区还是运动反馈；按视觉影响选，API陌生度不是优先级 |
| 定输入与上下文 | 将目标关系拆成可独立修改的宽/深、平面/角过渡、凹入、接触或材料区域等设计量，明确其消费者；保留结构过渡两侧、环境相邻层、实际受光与反射来源。单个输入不能表达差异时，在此换表示或增加控制量 |
| 做有区分力的比较 | 在代理/现有场景替换这段样件；保留可用基线，改变当前未知对应的输入，其余条件尽量固定。灰模看形体，最终材料看响应；动作样件当时做最小绝对时间求值与连续片段。先确认输入起作用，再判断是否更接近目标 |
| 作选择再扩展 | 按实际画面选择表示/参数；将完整关系的几何、锚点和材料区域作为复用单位。扩展时按场景组填入形态族与受控变化；每次移动/删减遮挡组，连同邻层重排。简单部位或相同表示/景别的已有证据可继承 |

对阶段2记录的共享语义场或布局来源做一次可观察的消费者检查：显示字段值/遮罩/曲线/点位，或用中性颜色标出实际输出；改变一个有意义的输入，核对预期的几何、落点/朝向及材料/FX消费者确实随之更新。若该规律由手工布局表达，就检查同一份布局数据被需要的路径、支撑和资产读取。字段定义存在但未接入下游，或布局数据各处重复硬编码，均返回对应生成器修正。

中层样件放行后，细节群体不能直接靠增加实例扩展；按[细节与分布SOP](detail-distribution.md)先生成区域计划、目标数量和实际放置清单，再捕获分布图、整场上下文与代表近景。逐组运行`validate_delivery.py ... --through detailDistribution`；欠覆盖、重复、越界或净空失败时停在分布阶段，修复后才进入lookdev。

形体与分布之间必须交接同一份几何原型目录：每个实际可见原型有稳定`variantId`，并能回溯到已通过`middleForms`的生成器/网格和代表视图；分布组只能引用这些ID，新增原型先回到`middleForms`制作并审核。`detailDistribution`只改变已批准原型的落点、朝向、经审定且不会改变身份比例的尺度范围和组内密度；明显改变主次比例或剪影的缩放要登记成新原型。分布可以决定原型出现在哪个语义区，却不能在散布代码里临时造新轮廓。若设计要求统一形体，明确写单一原型及原因，仍要审核布局节奏、覆盖和画面层级。完成后以同机位、同尺度、同灰模材质和目标分辨率查看原型并列图，再查看真实材质下的场景上下文；确认轮廓/体块差异可读、实例分布服从各区语义，且缩略视图中没有机械重复或噪声。报告里的不同ID、参数或截图数量不能替代这项视觉判断。

lookdev不要从整场整体加亮或叠滤镜开始。按[材质与灯光校准SOP](lookdev-calibration.md)将每个material feature连到真实材质绑定与受光/输出消费者，先定位瓶颈，再对当前一个变量做固定条件配对对照；保存几何、相机、分辨率、renderer、曝光与输出变换，查看真实Three.js基线/候选截图。覆盖全部材料特征并运行`validate_delivery.py ... --through lookdev`后，再进入最终运行相机样本；如果材质目标本身需要改形体或布局，回到middleForms或更早阶段，不能在lookdev偷偷更改空间关系。

数据读取或坐标一致的数值检查只证明参数传到消费者，不证明物体形成了目标中的空间关系。关键连接还要检查实际几何边界、间隙/搭接、支撑和接触，并在目标相机/可达视角中看最终结果；例如连接构件共享一个Z值，仍可能彼此断开、穿插或与承载路径错位。调试视图通过后恢复最终材光并复核完整画面；视觉关系未成立时回到布局或形体设计，不以代码审计通过代替审图。

用同工程隔离视图即可，不另建无关试片。形体/空间的构造方法见[构图与形体](composition-and-form.md)，材料/光影见[表面校准](surface-detail.md#3-先校准材料再回到完整镜头)，技术实现按[代码SOP](threejs-code-sop.md)选读。已有连贯部分保留；新引入的大占幅表示或反射场，在其上下文中先验证，再扩到整镜。

灰模检查体积、厚度、连接和支撑；最终材料检查反射/明暗边界、材料差异、空间层次和焦点。动作样件的证据覆盖事件前中后与连续过程；静态任务不制造额外动作。目标板与真实Three.js画面按同画幅/相近景别并排，主要局部以原尺寸看。先只看画面判断差距，再读实现说明，避免被代码数量和制作者描述引导。

分别记录：内容是否齐全；目标关系是否可读；执行品质相对基准还差什么。对visual-build-map中的每个高显著特征，记下实际捕获视图、可见实现、偏差和状态；代码里存在组件不代表画面里读得出来。写明最影响效果的实际差距及其责任层，修后在相同条件复看；有意偏离必须来自设计理由，不能事后降低目标。具备条件且获授权时用独立审阅；没有独立审阅时如实记录制作者自评范围。

**产物：**当前构建原尺寸彩图/必要灰模与局部、目标对照和差距结论；动作任务另含代表片段前中后帧、短连续片段与最小时间接口。按[核心镜头标准](validation.md#核心镜头放行标准)判断是否扩展。特征“都存在”但体积、材料或场景层次仍显著落后基准时，返回对应设计/生成层。

### 4. 动画、摄影与交互整合

在代表镜头与必要最小动作片段成立后，扩展到完整时长、其他镜头、次级动作、交互与声音整合。

镜头表记录`id / t0 / t1 / 必须看清的事件 / 主体锚点 / 相机 / 动作 / 环境反馈 / 声音 / 字幕区`。先设计关键状态和方向、速度、停顿、支撑/重心，再连接曲线；运动过程中的临时构图也需要成立。

实时播放、seek和导出共用完整的`stateAt(t)`/`renderAt(t)`。每次写完整基准状态后求姿态、相机、显隐、材质、FX和文字；不依赖上一帧。需要抽帧画风时量化指定层的求值时间，事件cue仍按精确主时间。累计物理/粒子使用重放、快照或缓存，详见[状态与规模](motion-and-scale.md)。

动作、接触与FX共用最终变形后的世界锚点。地表/水面、风、密度与反馈使用共享空间场；环境响应说明来源、方向、尺度、寿命和衰减。先完成主动作与因果反馈，再做次级动作和表面动态。声音使用同一cue表和独立轨道；有音频时以音频时钟驱动画面，play/seek/resume更新offset。

**产物：**关键事件前中后帧、连续片段、乱序seek及模式切换结果。检查接触、遮挡、运动稳定性、纹样附着与相机归属后，再导出最终文件。

### 5. 最终构建、运行与交付

冻结源码/资产版本、视口、fps、seed、质量档和入口。只从该版本构建最终HTML/媒体；失败目录的旧成片不作为本轮结果。同步与渐进渲染分别采用对应的捕获协议，见[渲染选择](rendering-choices.md)与[导出契约](validation.md#可执行离线影片导出)。

在用户实际打开的文件中检查开场、关键事件、结尾、连续播放与控件。自由查看实际完成一圈、至少8方位及俯仰/远近端点；双模式分别操作。按目标设备检查流畅度、资源与错误；视频核对帧数/时长/分辨率/fps/音轨，有声音审听最终混音。工具故障时具体标记未验收能力。

**交付包：**最终可打开文件、源码入口与必需资产、依赖版本及可重建的构建/运行命令、资源来源/许可、当前版本的视觉/交互/声音/性能证据和边界。用户要求成品时，不把内部原型当成最终交付。

## 返工与阶段衔接

每个问题记录：`镜头/时间/区域 → 可见症状 → 已确认根因 → 负责的生成器/资产/相机/材质层 → 改动 → 新证据`。局部改动先检查受影响帧与连续片段；共享规则改变、阶段合并和最终交付扩大到全片。连续两轮无对应可见改善时，重查上游设计与表示，停止同层调参。

## 按职责组织制作与集成

一个执行者也可顺序承担以下职责；使用多Agent须符合当前授权和工具规则。复杂制作分派时，以当前批次为边界，提供目标、上游实际产物、允许编辑文件、接口、可见完成依据和本批结束点。总目标留在制作规格；主负责人先查看本批画面与实现，再内部交接下一批，继续完成已授权制作。明确其他执行者也在工作，保留他人改动。

| 职责 | 唯一维护的内容 | 交接内容 |
|---|---|---|
| 导演/集成 | 制作规格、镜头/cue、全局空间/渲染契约、相机与共享入口 | 当前视觉规则、接口及最终组合画面 |
| 主体/角色 | 自有模型、材料、姿态/变形 | 造型、可见性、最终变形后表面/锚点 |
| 环境/道具 | 自有场景、空间布局与支撑面 | 尺度、接触定义、实例和锚点 |
| FX | cue与运动/接触派生的效果 | 来源/寿命、数据消费者、预算 |
| 声音 | 旁白、音乐、音效及混音 | cue、稳定媒体版本、试听结果 |

共享文件与每镜相机/LOOK各有一个写入者。先稳定上游接口，再安排独立消费者；强耦合形体与绑定、摄影与构图统一协调。模块成功加载后仍须审查组合镜头。
