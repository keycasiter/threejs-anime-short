# 材质与灯光校准 SOP

> 制作方式：通用算法与视觉判断按需使用；本文的manifest字段、固定阶段顺序和逐阶段脚本放行适用于显式选择的[正式阶段协议](formal-stage-workflow.md)。默认制作按[生产流程](production-workflow.md)推进完整代表关系，计划请求仅交计划。


本阶段将视觉分析中的材料目标转为可追溯的 Three.js 材质、灯光和输出响应，并在锁定的视角与渲染条件下做对照。输入是通过 `detailDistribution` 的当前场景、`visual-build-map.json` 与 `asset-ledger.json`；输出是校准报告、配对截图和被选择的参数/实现。进入此阶段不移动主体、重排场景或补散布细节；若视觉关系需要改变，回到对应上游阶段。

## 1. 从可观察目标开始

每个 `category: material` 特征逐一转成目标画面信号：哪些区域需要分开、哪些转折需要受光、反射带应该如何揭示曲率、暗部要保留多少信息，以及哪些变化在目标景别中必须可见。目标描述要能从截图判断，例如“湿润的窄带沿迎浪边连续可读，岩面保持粗糙暗面”，不要写“更电影感”“更真实”。一个资产族内材料语义接近的特征可以合并为一组，但每个特征只能归属一组，不能遗漏难表现的材料目标。

同一响应链要追到实际渲染消费者：

```text
参考观察 / visual-build-map feature
  → 材料区域、主方向、尺度与目标反射
  → Three.js材质绑定 + 灯光/环境输入
  → renderer与输出变换
  → 当前资产的目标像素证据
```

记录负责绑定材料的代码符号，以及实际参与的灯光或渲染输出符号。变量、材质参数或 shader 定义存在，并不说明目标对象真的使用它。大型资产族或材质跨资产复用时，先找一个覆盖关键曲率、分区和反射的代表样件，再把选定配置扩展到场景；无关构件不要为了统一而套用同一材质。

## 2. 先定位瓶颈，再做受控对照

在目标资产和最终环境里观察目标区域。遇到缺陷先按症状选择最小的诊断变量：

| 现象 | 优先排查 | 代码侧核对 |
|---|---|---|
| 所有表面都亮/灰、对比压平 | 曝光、色彩空间、tone mapping、环境强度 | renderer/output pass和最终颜色消费者；避免材质颜色与曝光同时改 |
| 曲面发塑料、材质彼此同质 | roughness/metalness、倒角与法线、环境反射带 | PBR通道语义、贴图色彩空间、真实mesh上的反射 |
| 主体轮廓与转折读不出 | 主光方向/大小、背景亮度、受光法线 | 灯的target、shadow camera、实际接收面和法线 |
| 阴影脏、漏光、漂浮或黑块 | shadow bias/normal bias、范围、接触几何 | 当前灯型和shadowMap算法真正读取的字段；接触区域几何 |
| 湿面/玻璃/水没有目标反应 | IBL预过滤、roughness、透射/透明排序、前后遮挡 | scene/material envMap优先级、深度与混合状态、实际曲面 |
| 细节随距离闪烁或变噪点 | 高频法线/粗糙度/纹理密度、mipmap与LOD | 像素投影尺寸、UV物理尺度、屏幕空间采样 |

每组选择一个主要变化量，设置“基线”和“候选值”。相机、分辨率、几何/布局、renderer版本、曝光、tone mapping、输出色彩空间和未测试参数固定。切换的变量应写出两侧具体值和原因；若主光与曝光都可能有问题，分别做配对实验，不同时改两个因素后把结果归功于其中一个。不同组可使用不同诊断视角，但每一组内的基线与候选必须使用同一视角与相同冻结控制。

不是每个变量都需要渲染一整套消融。选择能判断当前疑问的最少对照。先用中性小样分清“材质本身的问题”与“环境反射/灯光的问题”，再回到最终实际资产、实际环境和上下文，避免只在无关球体上调出好看的材质。

## 3. 生成可比较的 Three.js 证据

每组输出一对真实渲染PNG：`baseline` 和 `selected`。二者属于同一个 `lookdev` build，使用相同 `cameraId`、图像尺寸和冻结控制；图像长边至少 640 像素、短边至少 320 像素。视角应能同时暴露目标材料和它所依附的形体；若目标响应只在背面、掠射角或透明遮挡下可见，为该组增补对应视角，而不是用正面主图代替。

截图需由目标Three.js场景/实际材质消费者渲染，不用AI生成图、程序绘制图、灰模或后期合成替代。对照时保持项目真实的色彩链：输入颜色按sRGB语义解码，在工作空间受光，按项目输出pass进行tone mapping与显示转换。roughness、normal、metalness、mask等数据图不标作颜色。每一项数值都按当前安装版本/renderer验证其实际消费者；旧教程字段可被JavaScript接收，不代表渲染器会读取。

使用差分图或直方图时，只把它们当定位工具：微小像素变化、总体亮度提升和全图均方误差都不能证明目标信号变好。对照截图需人工回答：

- 目标材料分区是否变得可辨，并仍服从其构造/形成方向？
- 受光是否读出了形体，而不是把细节压成白亮边或黑暗噪声？
- 与相邻材料/背景的对比是否恰当，焦点是否仍清楚？
- 近、中、远景以及要求的侧/背/环绕视角里，响应是否保持有用且不闪烁？
- 候选值是否实现目标，且没有引入材质漂移、漏光、接触丢失或其他新问题？

报告里的 `decision.observation` 写可见差异和被选择的原因。若无可辨改进或带来新缺陷，不能写 `SELECTED` 并放行：继续诊断，或记录真实未解决原因并阻断阶段。

## 4. 参数扩展与验收边界

对照选定后，仅把参数扩展到设计上属于同一材料族/灯光角色的对象。不要把一个局部补光复制到整场，也不要通过普遍提亮来弥补没有反射内容、结构厚度或正确法线。回到完整场景的原相机与所有要求视角，确认材质不会吞没空间层次、细节节奏、焦点或阴影接触；完整画面最终审查仍由 `visualReview` 对当前运行构建负责。

`lookdev-report.json`逐组记录：family与全部材料feature ID、目标响应、材料绑定和灯光/输出代码符号、被改变的变量与两侧值、冻结条件、配对截图哈希和目视选择理由。每个视觉分析映射的material feature都需有覆盖。运行：

```bash
python3 <skill-root>/scripts/validate_delivery.py <project-root>/delivery-manifest.json --through lookdev
```

该门禁检查特征/资产族覆盖、输入哈希、源码符号声明、真实PNG格式/尺寸以及对照控制字段；它无法证明代码调用关系、截图确实来自所声明的设置，也不判断美感。人工必须打开对照图、确认控制条件和真实mesh，然后才能将组及阶段标为通过。最终 `visualReview` 仍需覆盖整个相机包络和全部资产族；lookdev对照通过不能代替最终场景验收。
